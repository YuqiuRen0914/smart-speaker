# Mac 大肥鱼助手

2026-11-12。用户已确认 Cute F6 试听，选择所有助手回答使用此声线、DeepSeek API、
本机 Mac 常驻、称呼“主人”的桌宠性格，并接受优先保留声线而增加等待。
本文件记录本轮方案；此前小智官方与 LunarLink 的历史验收仍保留原适用范围。

## 实现

音箱原收音与端点检测 → 16 kHz / 单声道 / 60 ms Opus → Mac SenseVoiceSmall INT8 →
DeepSeek Flash（关闭思考）→ FeiyuVoice Cute F6 → 24 kHz / 60 ms Opus → 原音箱播放器。
音频先整句合成，再按 60 ms 实时发送，避免推理慢于播放造成句中断续。
ASR 和 TTS 共用一个受监督的常驻推理进程；LLM 和 flow 用 MPS，HiFT 保留 CPU 原算法。

固件 `CONFIG_LUNAREDU_ASSISTANT_MAC` 是独立平台选择，继续复用当前 Pet 会话、
MQTT/UDP、取消与打断、单轮结束、音乐焦点及恢复所有者。
宏 `ASSISTANT_USE_MAC` 只扩展这一配置的传输，不改变官方小智或 LunarLink 的线上协议。
Mac 配置保存在独立 NVS 命名空间 `mac_assistant`；启动重新 bootstrap，不读取官方凭据，
没有自动切回官方声音的路径。源码默认仍保留官方配置；本机受管构建使用私有 Mac profile。

Mac 服务使用单设备、局域网部署。bootstrap 使用单独随机令牌请求头，MQTT 使用独立
账号、密码和上下行主题 ACL；DeepSeek 密钥只存 Mac，不进入固件、请求日志和报告。
本地 HTTP/MQTT 为可信局域网配置，不对公网发布。私有 token 存在本机构建配置和镜像内，
分发源码不携带它。Mac 主机名使用 `.local`；固件已启用 lwIP mDNS 查询。

每轮 listen start/detect 带递增 `turn_id`。回复控制消息和 UDP 包必须匹配当前轮，
取消、换会话、断线及 Mac 睡眠间隔使旧输出失效。UDP 的时间字段在 Mac profile 中承载
轮次；方向单独区分，序号步长 128，避免此用途下不同 AES-CTR 数据包使用重叠计数块。
Mac UDP 最大载荷 1468 bytes，重复、旧包、错误长度及不同连接标识被拒绝。
实体麦克风与静音探测都发送相同的轮次字段。每次 MQTT connected（包括库自动重连）
重新订阅并握手；新密钥会话的首个静音探测只建立 UDP 回传地址，不作为旧轮录音接收。
Mac 模型预热期间到达的 hello 保留到就绪后处理。

设备 MCP 工具目录从当前连接读取，DeepSeek 仅调用已发布工具；写操作不自动重试，
`accepted` 不等于物理动作完成。Mac 故障由原会话退出与焦点释放路径处理，显示
“助手暂不可用”，音乐等本地功能继续。服务恢复后原 MQTT 退避重连建立新会话。
实机发现点歌工具在语音焦点仍有效时直接启动播放器，导致音乐与 TTS 抢占 I2S。
修复由原播放器队列执行：语音持有焦点时保留已接收命令，焦点暂停命令优先，
最后语音 DMA 排空并释放焦点后按原顺序执行音乐命令。播放器忙时不丢弃已入队命令；
焦点获取与播放器命令共用原操作锁，文字测试也必须取得语音焦点。

## Mac 运行与恢复

源码统一维护在仓库的 [`tools/mac-assistant/`](../../tools/mac-assistant/README.md)，
从原 `声屿STUDIO/voice-lab` 本地仓库迁入，不导入原仓库历史或运行资源。
原本机入口保留为兼容链接；后续源码更新与提交均在 smart-speaker 中完成。

后台服务安装在 `~/Library/Application Support/ShengyuVoice/`，用户级 launchd label
为 `local.shengyu.feiyu-voice`。登录启动，崩溃后受监督重启；不注册系统级 daemon。
启动、停止、重启、状态入口由该目录中的 `.command` 提供。停止服务一并关闭 MQTT、UDP、模型进程。
只有接电且服务运行时才持有 `caffeinate -i`，拔电检测周期 2 秒；屏幕可休眠，
手动休眠和合盖不被阻止。睡眠/时钟间隔超过 5 秒使会话失效并重建整个传输。
