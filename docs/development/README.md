## 2. 三类信息必须区分

- **已确认**：用户确认的产品目标与行为，集中记录于产品规格。实现不得擅自缩减或替换。
- **推荐方案**：技术方案、阶段拆分和初始验收方法。可在既定目标内由实现者据证据完善，涉及重要边界变化时记录原因。
- **待验证／待决**：上游固定版本、240×240 视觉参数、动画格式、性能预算等。不能写成用户已确认或工程已具备。

当前实现事实看源码；历史实体验收看基线修正记录；未来目标看本组文档。三者不能互相替代。发现冲突先指出具体位置，保留历史记录，修订适用的现行文档。

## 3. 不可遗漏的约束

1. 以用户确认的 **1.0.35 + 当前接线 + 已有修复** 为开发起点；允许按本计划演进 UI，不允许更换成另一版整套产品。
2. ESP-IDF 6.0.1，当前 LVGL 锁定版本 9.5.0；不为移植方便擅自升级、降级或并存两套 LVGL。
3. AmoledOS 复用实际列表／导航代码并适配；当前大肥鱼复用素材与行为规则；现有音乐、音频、语音和显示能力优先复用。
4. 五个业务模块和独立设置入口是首发完整范围。中间阶段可以有明确标识的占位页面，首发不接受占位实现。
5. 页面、本地网页和 AI 操作同一业务状态；屏幕、音频硬件和关键资源有明确的唯一所有者。
6. 不覆盖现有工作区修改，不导入外部 LunarOS SDK、原私有产品树、凭据或设备日志。
7. 编译成功、已安装、真机可用、整体验收通过是不同结论，逐项提供证据。

## 4. 交给 AI 的首个任务

可直接复制下面的任务，不需要再复述全部聊天：

> 请按 `AGENTS.md` 和 `docs/development/README.md` 的阅读顺序执行，遵守 `04-ai-development-rules.md`。本次只执行 `03-implementation-plan.md` 的 P0：核对当前基线和实际能力所有者，固定 AmoledOS 与当前版大肥鱼来源，完成兼容性分析，补齐 P1 所需的界面入口、资源预算验证方法与任务拆分。先查源码，说明拟改文件及验收方法，再完成该任务范围内的工作。P0 以文档和检查为主，不借此替换桌面、播放器或 SDK，不进行烧录、OTA、提交、推送。用“已确认／已验证／待验证／阻塞”分别报告结果；缺少硬件、凭据或素材时继续完成无依赖工作，并准确标明未验证项。

后续任务使用开发准则中的任务卡，指定阶段或完整功能切片。没有阶段指定时，先从 P0 检查已有产物，避免重复做已经完成的工作。

如果要授权 AI 持续推进整个开发，可改用：

> 请依据 `AGENTS.md` 和 `docs/development/` 完成本项目首发开发。先核对并补齐 P0，再按实际依赖持续推进 P1–P6；复用已完成能力，每次形成一个完整切片并记录验证和遗留项。遵守 AI 开发准则，不因一次阶段总结就停止已授权的后续工作，不用未验证结果宣称整体完成。需要硬件、服务凭据或另一操作系统时，明确记录受影响的验收项，继续完成其他独立工作。保留当前工作区修改；烧录、OTA、提交、推送和发布另按明确授权执行。

## 5. 状态维护

本次仅创建规划文档；P0–P6 尚未按本计划验收。现有工程的音乐等能力不因此变为“从零开发”。后续执行者在 `implementation-status.md` 中追加任务状态和证据链接，格式见实施计划；完成一个切片就记录一次，不等到全部结束才补日志。

每次交付至少说明：完成范围、涉及文件、验证命令及结果、真机证据或缺口、遗留问题、下一步。任务状态不能只有一个含义模糊的“完成”。
